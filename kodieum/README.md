# «Кодиеум» — механизм инкапсуляции ключа на кодах Гоппы

Реализация по проекту методических рекомендаций ТК 26 (далее — МР) на
собственных ГОСТ-примитивах из [`gost/`](../gost): «Стрибоге-256» и
«Стрибоге-512», «Кузнечике» и построенном на них KDF_TREE. Сторонних
криптографических библиотек нет.

Реализовано всё, что описывает МР:

- KeyGen, Encaps, Decaps (раздел 8) и KeyGen2/Decaps2 (8.1.1, 8.3.1);
- режим без предварительного согласования параметров (раздел 7);
- выработка shk «Стрибогом-512» вместо H₂₅₆ (раздел 7);
- наборы параметров secparam1264, secparam1396, secparam14128 (приложение А).

## Требования и запуск

- **Python 3.10 или новее** (проверено на 3.14.8). Нужен из-за `int.bit_count()`
  и записи типов `list[int] | None`.
- **Зависимости:** для самой реализации — только стандартная библиотека и
  каталог `gost/` этого репозитория; для тестов — `pytest`. Список — в
  [`requirements.txt`](../requirements.txt) в корне.

Все команды — из корня репозитория:

```bash
pip install -r requirements.txt
python -m pytest kodieum/tests -v
python -m kodieum.examples
```

Ожидаемый итог тестов — `83 passed, 2 xfailed`, около 15 с. Два `xfailed`
— шаг 2 примеров Б.3 и Б.5, которые не воспроизводятся (см. ниже).
`python -m kodieum.examples` показывает каждое контрольное значение
приложения Б: вход, ожидаемое по документу, результат программы и
PASS/FAIL. Итог — `PASS 31, FAIL 5 из 36`, все FAIL — в том же шаге 2.

## Использование

```python
from kodieum import kem, unagreed
from kodieum.params import SECPARAM1264

pk, sk = kem.keygen(SECPARAM1264)        # pk — матрица A, sk = (seed2, salt)
shk, enk = kem.encaps(SECPARAM1264, pk)  # shk — 32 байта, enk — синдром s
assert kem.decaps(SECPARAM1264, sk, enk) == shk

pk, sk2 = kem.keygen2(SECPARAM1264)      # sk2 = (ℓ, salt)
shk, enk = kem.encaps(SECPARAM1264, pk, long_key=True)   # shk — 64 байта, «Стрибог-512»
assert kem.decaps2(SECPARAM1264, sk2, enk, long_key=True) == shk

pk, sk = unagreed.keygen(SECPARAM1264)   # pk = (A, t), sk = (seed2, salt, p)
shk, enk = unagreed.encaps(pk)           # n и m выводятся из A и t
assert unagreed.decaps(sk, enk) == shk   # n, m, t — из длин salt, p и s
```

Векторы хранятся как целые числа: бит i числа — элемент b_i вектора
(раздел 5.2 МР). Строка i матрицы A — число, бит j которого равен a_{i,j}.
В режиме без согласования длины несут информацию, поэтому salt, p и s там
хранятся в `BitVector`, а A — в `Matrix` вместе с числом столбцов.

## Принятые трактовки

МР в ряде мест допускает несколько прочтений. Ниже — что выбрано и почему;
подробно с вариантами исправления текста — в [`ANALYSIS.md`](ANALYSIS.md).

- **H₂₅₆.** Байты, сериализованные по Б.1, подаются в «Стрибог» как
  число в записи ГОСТ 34.11, старшим байтом вперёд, и хэш-код читается
  так же: `streebog256(data[::-1])[::-1]`. Только так сходятся хэши Б.1.
- **E_K («Кузнечик»).** Ключ, номер блока и результат — числа в записи
  ГОСТ 34.12: `Kuznechik(k.to_bytes(32, "big")).encrypt(i.to_bytes(16, "big"))`.
  Только так сходится Б.2.
- **Сериализация (Б.1).** Вектор длины ℓ — ⌈ℓ/8⌉ байт, b₀ — младший бит
  первого байта. Матрица и список векторов — поэлементно.
- **HKDF.** KDF_TREE_GOSTR3411_2012_256 с пустыми label и seed, R = 1.
  Ключ сериализуется по Б.1, результат читается как вектор по тому же
  правилу.
- **Решение системы в Decode, шаг 17.** Гаусс по столбцам y₀…y_t,
  z₀…z_{t−1}, последней свободной неизвестной — 1. Так совпадают y и z из
  Б.4; в МР нормировка не задана.
- **Проверка синдрома в Decaps.** Decode из 6.3 изредка возвращает e
  веса t с чужим синдромом, а шаг 4 Decaps требует e·(I ‖ A)ᵀ = s.
  Поэтому результат Decode сверяется с s, при несовпадении — отказ.
- **m в режиме без согласования.** МР пишет «m — длина вектора p», но у p
  только m − 1 координат; взято m = длина p + 1.
- **«Стрибог-512».** Заменяет H₂₅₆ во всех трёх местах выработки shk,
  включая отказ; порядок байтов — как у H₂₅₆. Примеров в МР нет.
- **shk.** Функции возвращают shk байтами хэш-кода. В Б.6 тот же ключ
  записан как вектор в записи Б.1, с переставленными полубайтами:
  `c1e8d97c…` у программы и `1c8e9dc7…` в документе.

| Б.3 и Б.5, шаг 2 | выработка seed′ ‖ v и seed₂ ‖ seed′ ‖ salt через HKDF | **FAIL** |

### Почему не сходится HKDF

Реализация KDF_TREE в `gost/kdf.py` совпадает с примерами RFC 7836. Но
значения из шага 2 примеров Б.3 и Б.5 не получились ни при одном из
перебранных вариантов:

- ключ: big/little-endian, с обратным порядком битов, дополнение слева и справа;
- хэш: «Стрибог-256» в записи RFC и в записи ГОСТ, «Стрибог-512»;
- поле [L]_b: разные кодировки и значения L, с разделителем 0x00 и без него;
- результат: разные способы чтения, выработка частей отдельными вызовами.

Все остальные шаги сходятся, если взять seed′, v и seed₂ из документа.
Поэтому вероятнее всего, что примеры готовились по соглашению, которого
нет в тексте МР, или содержат ошибку (`ANALYSIS.md`, предложение 2).

## Ограничения

- Нет защиты от атак по времени: умножение в поле табличное, Decode
  ветвится по данным.
- Байтовые форматы ключей и шифртекста не вводились: МР их не определяет
  (`ANALYSIS.md`, предложение 8).
- n должно быть кратно 8: наша KDF_TREE вырабатывает выход целыми байтами.
  Наборы приложения А этому удовлетворяют.
