# Анализ качества проекта «Кодиеум» (черновик, пополняется по ходу реализации)

Формат по разделу «Анализ качества проекта» МР: место → проблема → почему
проблема → предлагаемое изменение.

## 1. E_k(i) в gen_unique_seq (раздел 6.1, шаг 1)

**Место:** раздел 6.1, шаг 1: «Для каждого i = 0, 1, ..., 2^m − 1 положить
a_i = E_k(i)».

**Обнаруженная проблема:** не определено, как целое число i (от 0 до 2^m − 1)
сериализуется в 128-битный входной блок шифра Кузнечик. Раздел 5.2 задаёт
соответствие между двоичным вектором и целым числом (a = Σ aᵢ·2ⁱ), но не
указывает explicit, какой байтовый/битовый порядок использовать при упаковке
произвольного целого i в блок фиксированной длины 128 бит для входа в
блочный шифр.

**Почему это проблема:** при реализации «с нуля» (с использованием сторонней,
но ГОСТ-совместимой библиотеки Кузнечика, прошедшей проверку по
официальному тестовому вектору ГОСТ Р 34.12-2018 / RFC 7801) не удалось
воспроизвести контрольный пример из Приложения Б.2 ни при одном из
опробованных вариантов: i как big-endian или little-endian 128-битное целое,
ключ k как есть или декодированный согласно табличной hex-нотации
Приложения Б.1, перестановка 128-битных половин 256-битного ключа. Это
означает, что без знания точного соглашения, использованного авторами при
подготовке контрольного примера, независимая реализация не может быть
автоматически верифицирована этим примером — то есть именно та ситуация,
которую контрольные примеры призваны исключить.

**Предлагаемое изменение:** явно указать в разделе 6.1 (или в разделе 5.2),
что целое i представляется в виде 128-битного вектора согласно
соответствию из 5.2 и правилу сериализации вектора в байты из Приложения
Б.1 (байт 0 = младшие 8 бит и т.д.), либо явно сослаться на используемый в
ГОСТ 34.12-2018 способ представления целых чисел в виде блока данных.
