# Декомпозиция алгоритма «Гиперикум» на составляющие

Настоящий раздел выделяет из текста проекта методических рекомендаций
алгоритмы, подлежащие программной реализации, и указывает их входные/
выходные данные и последовательность выполнения.

«Гиперикум» — постквантовая **схема цифровой подписи без сохранения
состояния** (stateless hash-based signature, по образцу SPHINCS+), в
отличие от Кодиеума и Земляники, которые являются схемами инкапсуляции
ключа. Стойкость основана исключительно на стойкости хэш-функции
(Стрибог), а не на теоретико-кодовых или решёточных задачах.

## 1. Математический фундамент (раздел 4.5.1)

Преобразование байтовой строки в целое число и обратно (big-endian).
Используется как базовая утилита для разбора полей адреса, подписи,
индексов — минимальная часть, без собственной арифметики (в отличие от
Кодиеума и Земляники здесь нет конечного поля или кольца — вся схема
построена поверх хэш-функции).

## 2. Внешний криптопримитив

Единственный примитив — хэш-функция Стрибог (ГОСТ 34.11-2018) с длиной
выхода 256 и 512 бит. Поверх неё документ определяет семейство
**настраиваемых хэш-функций** (раздел 4.2, 4.3, формулы раздела 4.10):
`Th_l`, `Th_k`, `F`, `H`, `H_s`, `PRF`, `PRF_msg`, `H_msg` — каждая просто
конкатенирует свои аргументы в фиксированном порядке и хэширует
Стрибогом. Эти функции — тонкий слой над одним примитивом, не
самостоятельный алгоритм.

## 3. Адресация (раздел 4.4)

Структура `ADRS` (224-битный адрес) — контекстная метка, уникальная для
каждого вызова хэш-функции в дереве, предотвращающая коллизии между
разными частями схемы. 8 типов адресов (раздел 4.4.1), каждый со своим
форматом суффикса. Это не алгоритм, а структура данных с полями и
сеттерами/геттерами (`УстановитьУровень`, `УстановитьДерево`,
`УстановитьТип` и т.д.).

## 4. Вспомогательные схемы (раздел 4.6–4.9)

Собраны в порядке возрастания сложности — каждая следующая использует
предыдущую как «лист» дерева:

| Схема | Назначение | Раздел |
|---|---|---|
| WOTS+C | одноразовая подпись (подписывает 64 блока по 4 бита = 256 бит сообщения через хэш-цепочки) | 4.6 |
| XMSS | дерево Меркла высотой h' из открытых ключей WOTS+C | 4.7 |
| Гипердерево (HT) | d слоёв деревьев XMSS, верхние подписывают корни нижних | 4.8 |
| FORS+C | few-time подпись хэша сообщения (лес из k' деревьев) | 4.9 |

Каждая из них имеет единый паттерн: `SKgen`/`PKgen` (выработка ключа),
`Sign` (подпись), `pkFromSig` (восстановление ключа проверки из подписи
— «Гиперикум» использует **неявную проверку**: явного отдельного шага
verify для WOTS+C и FORS+C нет, вместо этого из подписи вычисляется
элемент ключа, который используется выше по дереву).

## 5. Основной процесс (раздел 5)

Собирает все вспомогательные схемы в одну подпись: `Hypericum.KeyGen`,
`Hypericum.sign`, `Hypericum.Verify`.

### 5.1 KeyGen (раздел 5.4)

**Вход:** нет (использует только параметры схемы).
**Выход:** открытый ключ `PK = (PK.seed, PK.root)`, закрытый ключ
`SK = (SK.seed, SK.prf, PK)`.

Последовательность: генерируются три случайных 256-битных значения
(`SK.seed` — для всех секретных ключей WOTS+C/FORS+C, `SK.prf` — для
детерминированной рандомизации подписи, `PK.seed` — общедоступное
начальное значение для всех хэш-вызовов); `PK.root` вычисляется как
корень гипердерева верхнего уровня.

### 5.2 Sign (раздел 5.5)

**Вход:** сообщение `M`, закрытый ключ `SK`.
**Выход:** подпись `SIG = (R, s, SIG_FORS, SIG_HT)`.

Пять этапов: 1) вычислить случайное/детерминированное зерно `R`;
2) вычислить хэш-код сообщения и из него — индексы дерева FORS+C и
листа гипердерева (с перебором счётчика `s`, пока не выполнится условие
на младшие биты — аналог proof-of-work внутри подписи); 3) подписать
хэш сообщения схемой FORS+C; 4) вычислить ключ проверки FORS+C из
полученной подписи (неявная проверка); 5) подписать этот ключ
гипердеревом.

### 5.3 Verify (раздел 5.6)

**Вход:** сообщение `M`, подпись `SIG`, открытый ключ `PK`.
**Выход:** результат проверки (успех/неудача).

Повторяет вычисление хэш-кода и индексов, затем восстанавливает ключ
проверки FORS+C из подписи и проверяет подпись гипердерева относительно
`PK.root` — вся проверка сводится к одному сравнению в самом конце
(`HT.verify`), всё остальное — пересчёт промежуточных значений.
