# «Гиперикум» — подпись на функции хэширования без сохранения состояния

Реализация по проекту методических рекомендаций ТК 26 (далее — МР) на
собственном «Стрибоге» из [`gost/`](../gost). Сторонних криптографических
библиотек нет. Схема — того же семейства, что SPHINCS+: одноразовая
подпись WOTS+C, деревья XMSS, гипердерево и лес FORS+C.

Реализовано всё из МР: функции раздела 4.10, адресация 4.4, WOTS+C,
XMSS, гипердерево, FORS+C, выработка ключей, подпись (режим по умолчанию с
opt_const и режим со случайностью) и проверка подписи для всех шести
наборов параметров таблицы 1.

## Требования и запуск

- **Python 3.10 или новее** (проверено на 3.14.8).
- **Зависимости:** для реализации — только стандартная библиотека и
  `gost/`; для тестов — `pytest` (`requirements.txt` в корне).

Из корня репозитория:

```bash
python -m pytest giperikum/tests -v
GIPERIKUM_SLOW=1 python -m pytest giperikum/tests -v
python -m giperikum.examples
python -m giperikum.examples --full
```

- Обычный прогон тестов — около минуты, долгие тесты пропускаются. Тесты
  по памяти — `tests/test_memory.py` (раздел 9 `REPORT.md`).
- `GIPERIKUM_SLOW=1` добавляет полную подпись трёх наборов «Б» со сверкой
  с документом и замер памяти подписи Б_128_20 (несколько минут).
- `examples` печатает по каждому контрольному значению: ожидаемое по
  документу, полученное программой и PASS/FAIL. Без `--full` — около 10 с,
  итог `PASS 71, FAIL 1 из 72`; единственный FAIL — опечатка документа в
  A.5. С `--full` добавляется ещё одна опечатка, в A.6 (см. ниже).

## Использование

```python
from giperikum import hypericum
from giperikum.params import B_128_20

pk, sk = hypericum.keygen(B_128_20)
sig = hypericum.sign(b"message", sk, B_128_20)              # режим по умолчанию
assert hypericum.verify(b"message", sig, pk, B_128_20)
sig2 = hypericum.sign(b"message", sk, B_128_20, randomize=True)  # режим со случайностью
```

Время на Python 3.14, Apple M5: для «Б_256_20» подпись около 40 с,
проверка около 1 с. Наборы «М» рассчитаны на десятки миллионов вызовов
хэш-функции при подписи (таблица 1), поэтому на Python практически не
подписываются, но работают на той же реализации.

Для скорости в `gost/streebog.py` добавлен табличный вариант LPS: тот же
результат, что у буквального, но в 12 раз быстрее. Без него подпись одного
набора «Б» заняла бы около 10 минут.

## Принятые трактовки

Подробно, с вариантами исправления текста, — в [`ANALYSIS.md`](ANALYSIS.md).

- **Подача данных в «Стрибог».** STR(A ‖ B ‖ … ‖ X) из раздела 4.10 —
  это «Стрибог» в порядке байтов RFC 6986 от X ‖ … ‖ B ‖ A: поля в
  обратном порядке, байты внутри каждого поля без изменений, результат не
  разворачивается. Так получаются R, digest и все остальные значения
  приложения А; варианты с разворотом байтов не дают ни одного совпадения.
- **Сообщение в примерах** подаётся с завершающим нулевым байтом, как
  строка языка C. Без него не совпадает уже R.
- **Целевая сумма S_{w,n}** = l·(w − 1)/2 = 480, а не l·w/2 = 512, как
  написано в 4.6.4. При 512 подпись остаётся верной, но не совпадает с
  приложением А.
- **Стек в treehash.** У пустого стека высота 0, лист кладётся с высотой 1
  (так записано в алгоритмах 11, 19 и в разделе 3.2).
- **УстановитьТип** меняет только поле «Тип»; остальные поля адреса
  сохраняются, как и сказано в разделе 3.2.

## Контрольные примеры приложения А

| Что сверяется | Наборы | Результат |
|---|---|---|
| R, digest, условие FORS+C, idx_leaf | все шесть | PASS |
| idx_tree | все, кроме М_256_20 | PASS |
| idx_tree в A.5 (М_256_20) | — | **FAIL**: напечатано значение из A.4 (250103), по digest получается 2246, и при нём сходятся WOTS_PK обоих слоёв |
| WOTS_PK на каждом слое (42 значения) | все шесть | PASS |
| верхний XMSS_PK равен PK.root | все шесть | PASS |
| PK.root по SK.seed и PK.seed | наборы «Б» | PASS |
| полная подпись: s, SIG_FORS, все слои SIG_HT, PK_FORS, XMSS_PK каждого слоя, проверка | наборы «Б» | PASS, кроме одного значения |
| последние 4 байта слоя 0 SIG_HT в A.6 (Б_128_20) | — | **FAIL**: напечатаны байты слоя 1; XMSS_PK слоя 0 из нашей подписи совпадает с документом, а с байтами из документа — нет |

Для наборов «М» деревья высотой до 2¹⁷ листьев и FORS с 2¹⁸ листьями на
Python за разумное время не строятся, поэтому для них проверено всё, что
не требует построения целого дерева.

## Ограничения

- Нет защиты от атак по времени.
- Подпись наборов «М» на Python занимает часы и дни (таблица 1: от
  2 до 545 млн вызовов Th).
