# Анализ качества проекта МР «Гиперикум» и предложения по улучшению

Анализ сделан с позиции разработчика, который впервые реализует схему
только по тексту проекта (далее — МР, вторая редакция). Каждое предложение
оформлено по шаблону задания: место в документе, проблема, почему это
проблема, предлагаемое изменение. Для спорных мест указано, как поступила
наша реализация. Все утверждения проверены на коде из этой папки.

## Ответы на главные вопросы

**1. Можно ли только по проекту создать однозначную и воспроизводимую
реализацию?** Нет. Структура схемы (адреса, WOTS+C, XMSS, гипердерево,
FORS+C, порядок вызовов) описана подробно и в целом верно, и после
подбора соглашений наша реализация воспроизвела все значения приложения А,
кроме двух ошибочных (A.5 и A.6). Но три вещи по тексту не определяются:

- в каком порядке байты подаются в «Стрибог» (предложение 1). Буквальное
  прочтение раздела 4.5.2 даёт другие значения;
- что подписываемая строка в примерах содержит завершающий нулевой байт
  (предложение 2);
- какая целевая сумма S_{w,n} используется (предложение 3): написанная в
  тексте даёт подписи, которые не совпадают с примерами.

Каждое из трёх мест мы нашли только перебором вариантов против
контрольных примеров. Кроме того, в псевдокоде есть ошибки, при буквальном
исполнении которых программа не работает (предложение 5).

**2. Какие изменения облегчили бы независимую реализацию?** Нормативное
описание подачи данных в «Стрибог» с примером; подписываемые сообщения
в примерах в виде байтов; исправленная формула S_{w,n}; исправленный
псевдокод алгоритмов 2 и 3; полные подписи в контрольных примерах (или
хотя бы их хэши) вместо первых и последних 4 байт; исправление опечаток
и нумерации. Подробно — ниже.

## Предложения

### 1. Порядок подачи данных в «Стрибог» описан неоднозначно

- **Место в документе:** раздел 4.5.2, формула (10); раздел 4.10,
  формулы (11)–(17); приложение А.1.
- **Обнаруженная проблема:** сказано, что Str «обрабатывает полученную
  строчку справа налево, начиная с X[s₁ − 1]», а строки «записаны в
  представлении big-endian». Отсюда естественно следует, что байты
  каждого поля подаются в обратном порядке. На деле значения приложения А
  получаются, только если подать в «Стрибог» (в порядке байтов
  RFC 6986) поля в обратном порядке, X ‖ … ‖ B ‖ A, а байты внутри полей
  и выход хэш-функции не разворачивать. Кроме того, формула (10) не
  содержит блока 0²⁵⁶, который есть во всех формулах раздела 4.10.
- **Почему это является проблемой:** у разработчика есть по меньшей мере
  четыре разумных прочтения (разворот всей строки, разворот полей,
  разворот выхода, их сочетания), и только одно совпадает с примерами. По
  тексту выбрать его нельзя.
- **Предлагаемое изменение:** заменить абзац после формулы (10) на

  > Значение Str(A₁ ‖ A₂ ‖ … ‖ A_r) есть хэш-код ГОСТ 34.11-2018 от
  > сообщения, байтовое представление которого по Р 50.1.113-2016 (первый
  > байт — младший) равно A_r ‖ … ‖ A₂ ‖ A₁, где каждое Aᵢ — байтовая
  > строка в порядке big-endian. Хэш-код записывается в том же порядке
  > байтов.

  и привести в формуле (10) блок 0²⁵⁶, как в (15). Полезен и пример:
  байты входа и выход F для одного конкретного ADRS.
- **Как поступили в реализации:** `hashes.py`, функция `_str256`.

### 2. Не указаны байты подписываемых сообщений

- **Место в документе:** приложение А, строки «Подписываемая строка».
- **Обнаруженная проблема:** сообщение дано как текст в кавычках. R и
  digest из примеров получаются, только если к ASCII-строке дописать
  нулевой байт (так строку хранит язык C). Об этом нигде не сказано.
- **Почему это является проблемой:** реализация, которая подаёт ровно
  текст, не совпадёт с примером уже на первом значении R, и разработчик
  будет искать ошибку в своём коде.
- **Предлагаемое изменение:** приводить сообщение в шестнадцатеричном виде,
  например «M = 4578616d…3634 00 (58 байт)», или явно указать, что
  строка завершается нулевым байтом.
- **Как поступили в реализации:** тесты и `examples.py` дописывают `\0`.

### 3. Формула целевой суммы S_{w,n} не совпадает с примерами

- **Место в документе:** раздел 4.6.4: «S_{w,n} = lw/2»; алгоритм 8.
- **Обнаруженная проблема:** при l = 64, w = 16 формула даёт 512. Подписи
  WOTS+C из приложения А получаются только при S_{w,n} = 480 = l(w − 1)/2:
  например, первый блок σ₀ подписи слоя 0 набора Б_256_20 (`f6106959…`)
  соответствует первому разряду 1, который даёт s = 14 при сумме 480.
  Значение S_{w,n} не указано и в таблице 1 параметров.
- **Почему это является проблемой:** при S_{w,n} = 512 подпись остаётся
  корректной и проходит проверку той же реализацией, но несовместима с
  любой реализацией, где взято 480. Такую несовместимость тестами
  «подписал — проверил» не обнаружить.
- **Предлагаемое изменение:** «S_{w,n} = l(w − 1)/2 = 480» в 4.6.4 и
  отдельная строка S_{w,n} в таблице 1 и в каждом наборе приложения А.
- **Как поступили в реализации:** `TARGET_SUM = 480` (`params.py`).

### 4. Ошибки в значениях примеров A.5 и A.6

- **Место в документе:** приложение A.5 (Гиперикум_М_256_20), значения
  idx_tree в процедурах выработки и проверки подписи.
- **Обнаруженная проблема:** напечатано 250103 — то же число, что в A.4
  для другого набора параметров. Из digest того же примера по шагам 15–17
  алгоритма 23 получается 2246, и при idx_tree = 2246 совпадают WOTS_PK
  обоих слоёв, приведённые в A.5.
- **Почему это является проблемой:** корректная реализация расходится с
  примером, и без проверки промежуточных значений слоёв нельзя понять, на
  чьей стороне ошибка.
- **Ещё одна ошибка того же рода:** в A.6 (Гиперикум_Б_128_20) у слоя 0
  SIG_HT последние 4 байта «b0 66 b1 30» совпадают с последними байтами
  слоя 1. По нашей подписи слой 0 заканчивается на «4e f2 41 98», и именно
  при этих байтах из подписи получается XMSS_PK слоя 0 из A.6; с байтами
  документа он не получается.
- **Предлагаемое изменение:** idx_tree = 2246 в A.5; «layer 0: 98 b4 cc ce
  … 4e f2 41 98» в A.6.

### 5. Ошибки в псевдокоде алгоритмов 2 и 3

- **Место в документе:** раздел 4.5.3, алгоритмы 2 и 3.
- **Обнаруженная проблема:**
  - алгоритм 2: цикл ведётся по i, а в теле используется необъявленная j:
    «S[n − 1 − j] := total mod 256»;
  - алгоритм 3: в условии цикла «j := i·b; i < (i + 1)·b; j + 1» проверяется
    i вместо j. При буквальном исполнении условие всегда истинно, и цикл не
    завершается.
- **Почему это является проблемой:** алгоритмы 2 и 3 используются при
  каждой подписи (алгоритм 3 — в алгоритмах 20 и 21), и буквальная
  реализация либо не запускается, либо зацикливается.
- **Предлагаемое изменение:** в алгоритме 2 «S[n − 1 − i]», в алгоритме 3
  «цикл j := i·b; j < (i + 1)·b; j + 1».

### 6. Противоречивое описание полей адреса

- **Место в документе:** раздел 4.4.1, абзац после перечня полей;
  разделы 4.4.4 и 4.4.5.
- **Обнаруженная проблема:**
  - «Адрес уровня i задает значение от 1 до d», а все алгоритмы используют
    уровни от 0 до d − 1 (алгоритмы 15–17, 23);
  - «дерево на уровне i из множества (h/d)^{i−1} деревьев», тогда как
    раздел 4.8.1 правильно говорит, что на уровне d − 1 одно дерево, на
    уровне d − 2 — 2^{h′} и так далее, то есть 2^{(d−1−i)·h′} деревьев;
  - в 4.4.4 «на уровне i индекс узла варьируется в диапазоне от 0 до
    2ⁱ − 1», хотя на высоте i в дереве высоты h′ узлов 2^{h′−i}; в 4.4.5 то
    же для FORS, где индекс к тому же сквозной по всем k′ деревьям.
- **Почему это является проблемой:** диапазоны полей адреса нужны для
  проверки корректности входов, а указанные в тексте неверны.
- **Предлагаемое изменение:** «Адрес уровня i принимает значения от 0 до
  d − 1; на уровне i расположено 2^{(d−1−i)·h/d} деревьев». В 4.4.4:
  «на высоте i индекс узла принимает значения от 0 до 2^{h/d−i} − 1». В
  4.4.5: «от 0 до k′·2^{b−i} − 1 (нумерация сквозная по всем деревьям)».

### 7. Расхождения между текстом и алгоритмами WOTS+C

- **Место в документе:** раздел 4.6.4 и алгоритмы 8–10.
- **Обнаруженная проблема:**
  - текст говорит «d = H(PK.seed, T, s ‖ M)», а алгоритм 8 использует
    H_s и адрес ADRS; буква d уже занята числом уровней;
  - разряды нумеруются то с единицы (a₁ … a₆₄, M₁ … M₆₄, алгоритм 10:
    «B := (b₁, …, b₆₄)», сумма от 1 до 64), то с нуля (алгоритм 9:
    b₀ … b₆₃, циклы i от 0 до 63 в обоих алгоритмах).
- **Почему это является проблемой:** при сдвиге нумерации на единицу
  цепочка i подписывается разрядом i + 1, и подпись перестаёт совпадать.
- **Предлагаемое изменение:** «… вычисляется хэш-код m = H_s(PK.seed, ADRS,
  s ‖ M)» и единая нумерация b₀ … b₆₃ во всём разделе 4.6.

### 8. Контрольные примеры не позволяют проверить подпись побайтно

- **Место в документе:** приложение А.1 («Для строк, превышающих по длине
  64 байта, приводятся только первые и последние 4 байта»).
- **Обнаруженная проблема:** от подписи длиной от 9772 до 59132 байт даны
  8 байт SIG_FORS и по 8 байт на каждый слой SIG_HT. Не даны счётчики s
  подписей WOTS+C на каждом слое. Проверку подписи из примера нельзя
  запустить, потому что самой подписи нет.
- **Почему это является проблемой:** реализация проверки подписи не может
  быть проверена отдельно от реализации подписи. Ошибка вроде описанной в
  предложении 3 обнаруживается только по первым 4 байтам слоя.
- **Предлагаемое изменение:** привести хотя бы для одного набора полную
  подпись (в электронном приложении) или хэш-код H₂₅₆ каждой части
  подписи и счётчик s каждого слоя.
